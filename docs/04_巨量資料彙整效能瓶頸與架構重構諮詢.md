## 2. 兩大核心彙整任務說明

### 任務一：【📊 彙整資料】（明細彙整與雙工作表活頁簿產出）
1. **輸入**：
   - 本地 `下載清單.csv`（記載下載狀態與檔案路徑）。
   - 本地數百個已下載的晶圓測試 CSV / TSV 文字檔。
2. **核心運算**：
   - 穿透讀取各文字檔，定位包含 `2D ID`、`X`、`Y`、`Unit BIN#` 的表頭行。
   - 依據層級目錄與 PN 錨點解析出 `RECIPE` 名稱。
   - 提取並產出 11 欄明細：`第 1 層目錄`, `PN`, `第 2 層目錄`, `LOT`, `RECIPE`, `檔案名稱`, `2D ID (MPID)`, `X (MP_X)`, `Y (MP_Y)`, `MPID_X_Y`, `Unit BIN#`。
3. **輸出**：`下載與明細彙整_YYYYMMDD_HHMMSS.xlsx`
   - **Sheet 1 (`下載清單`)**：表頭粗體、欄寬自適應。
   - **Sheet 2+ (`工作表2`, `工作表2_2`...)**：收錄 11 大欄位明細，達 100 萬列自動切頁，A~J 欄鎖定為純文字格式 (`@`)，依規格設定各欄固定欄寬。

### 任務二：【📊 彙整資料2】（PN/LOT/RECIPE 交叉樞紐分析與權重評級）
1. **業務背景**：
   - 原版功能由客戶以 **Excel VBA 巨集 (`ExportPNLOTRecipeWithBlankWarning`)** 撰寫，共 658 行代碼。
   - 我們將該 VBA 邏輯完整移植至 Python 引擎。
2. **輸入**：
   - 上一步產出的 `下載與明細彙整_*.xlsx`（就是那個 **77 MB、240 萬列** 的巨型檔案）。
3. **核心運算邏輯**：
   - **來源識別**：掃描該活頁簿中所有 A1 為「第 1 層目錄」之明細分頁。
   - **晶圓座標補零正規化**：將 `MPID_X_Y`（如 `ID_1_2`）尾端兩碼純數字自動補零為兩位數（`ID_01_02`）。
   - **LOT / PN 安全退避**：若 D 欄 LOT 為空則退避取第 2 層目錄去尾一碼；若 PN 為空退避取第 1 層目錄。
   - **群組樞紐轉置**：以 `(PN, LOT)` 與晶片 `MPID_XY` 為錨點，將縱向的 `RECIPE` 動態橫向展開為獨立欄位，單元格填入該晶片測得之 BIN 代碼（若多筆以逗點分隔）。
   - **晶圓級 BIN 權重判定 (BinCode Ranking)**：
     - 代碼中包含 `32` $\rightarrow$ 最高權重 Rank 3，輸出 `32`
     - 代碼中包含 `1` $\rightarrow$ 次高權重 Rank 2，輸出 `1`
     - 代碼中包含其他數值 $\rightarrow$ Rank 1，各 RECIPE 輸出 `others`，整列綜合判定輸出 `Others`
     - 空白或無測試 $\rightarrow$ Rank 0，輸出空字串
   - **異常 RECIPE 防呆**：若 RECIPE 為空值，動態歸入保留欄位 `ERROR_blank` 並置於最右側，且排除不參與整列 `BinCode_sumary` 判定。
   - **群組完整性保護與切頁**：若某個 LOT 晶片群組整包可放入新頁，則不在舊頁尾端拆碎分頁；達 100 萬列自動切頁。
4. **輸出**：`PN_LOT_RECIPE_明細與彙整_YYYYMMDD_HHMMSS.xlsx`
   - **`中繼明細_01` ...**：A: `PN`, B: `第 2 層目錄(LOT)`, C: `LOT`, D: `MPID_XY` + 各 RECIPE 原始 BIN 字串。
   - **`RECIPE彙整_01` ...**：A: `PN`, B: `第 2 層目錄(LOT)`, C: `LOT`, D: `MPID_XY`, E: `BinCode_sumary` + 各 RECIPE 權重結果代碼。
   - 表頭深藍底白字（RGB: 31, 78, 120），`ERROR_blank` 深橘底白字，純文字格式 `@`。

## 4. 遇到的具體問題與效能數據（現場重現）

### 痛點 1：【彙整 1】100% 時磁碟檔案停在 72 KB 長達 3～6 分鐘
- **現象**：
  進度條跑到 100%，日誌顯示「所有檔案解析完成，正在儲存 Excel 活頁簿至硬碟 (請稍候)...」。
  使用者打開目標資料夾，發現產生了一個 `下載與明細彙整_xxx.xlsx`，但**檔案大小死死卡在 72 KB**，幾分鐘毫無動靜。
- **原因診斷**：
  `openpyxl.Workbook()` 是全記憶體 DOM 模型。240 萬筆資料在記憶體中建立了超過 2,600 萬個 Python `Cell` 物件，耗用高達 **6 GB ~ 8 GB 記憶體**！
  當調用 `wb.save()` 時，第一步先寫入「Sheet 1 下載清單」，寫入磁碟約 72 KB；接著在背景單執行緒將 240 萬筆 Cell 轉換為 XML 字串並進行 ZIP 壓縮。在 ZIP 尚未完成封口（Close）前，Windows 檔案大小不會更新，導致使用者嚴重焦慮以為程式當掉。

### 痛點 2：【彙整 2】「光讀取資料表就花很久時間... 然後又要等產出... 感覺比 VBA 還慢」
- **實測耗時拆解（240 萬筆，77 MB 檔案）**：
  1. **讀取階段 (`openpyxl read_only=True`)**：
     需從 77 MB 的 ZIP 中解出 600 MB 的 XML，再用純 Python 逐個標籤 parse 出 240 萬列。
     **耗時：約 3.5 ～ 4.5 分鐘**！
  2. **記憶體分群與權重運算**：
     純 Python 字典操作，**耗時僅約 15 ～ 25 秒**（速度非常快）。
  3. **產出寫入與存檔階段 (`openpyxl.save`)**：
     寫入「中繼明細」與「RECIPE彙整」，再次在記憶體中建立數千萬個 Cell 並進行第二次 77 MB ZIP 壓縮。
     **耗時：約 3.5 ～ 5 分鐘**！
  4. **合計總等待時間：長達 8 ～ 10 分鐘！**

### 痛點 3：為什麼使用者會覺得「比原本的 VBA 還慢」？
- **VBA 的優勢**：
  原本的 VBA 是直接在**已經開啟的 Excel 視窗內部**跑。Excel 本身是微軟用 **C/C++** 寫的，數據早已以二進位矩陣載入記憶體中。VBA 呼叫 `ws.Cells(...).Resize(n, 2).Value2` 是直接做 C++ 記憶體指標複製，完全省去了「77 MB ZIP 解壓縮 $\rightarrow$ 600 MB XML 解析」的龐大開銷。
- **Python 目前的劣勢**：
  Python 作為外部程式，被卡在「**巨型 Excel 解壓縮讀取 $\rightarrow$ 記憶體暴增 $\rightarrow$ 巨型 Excel 重新打包壓縮**」的 I/O 與 XML 序列化泥淖中。

## 5. 我們已嘗試的初步驗證與思路

1. **驗證 OpenPyXL Write-Only 串流模式**：
   - 測試代碼：`openpyxl.Workbook(write_only=True)`
   - 實測結果：寫入 50 萬筆晶片，記憶體從 **1,765 MB 驟降至 45 MB**！最後存檔時間從 **24 秒縮短至 1.2 秒**！
   - 缺點/難點：Write-Only 模式下單元格只能循序 append，不支援常規的隨機單元格存取；樣式必須用 `WriteOnlyCell` 先包裝再 append；跨頁分頁與欄寬設定需謹慎處理。
2. **驗證 C 核心 `lxml.etree.iterparse` 串流讀取**：
   - 測試代碼：直接用 Python `zipfile` 讀取 `.xlsx` 內部的 `xl/worksheets/sheet2.xml`，透過 C 語言實現的 `lxml.iterparse` 捕捉 `<row>` 標籤。
   - 實測結果：30 萬筆讀取時間從 openpyxl 的 **29.3 秒驟降至 4.19 秒**（速度快了 7 倍）！
   - 難點：`.xlsx` 中的字串通常儲存在 `xl/sharedStrings.xml`，解析時需要自行維護 Shared Strings Table 映射，若實作不當容易出現編碼問題或記憶體暴增。
3. **資料流架構質疑**：
   - 「彙整 1」在解析那數百個原始 CSV 時，所有晶片數據其實已經在 Python 記憶體中跑過一遍了。
   - 目前的流程是：`原始 CSV -> 彙整 1 -> 寫入 77MB Excel -> 彙整 2 從 77MB Excel 重新讀入 -> 運算 -> 寫入第二份 Excel`。
   - 是否應該引入高速中間快取（例如 **Apache Arrow / Parquet / DuckDB / SQLite**）？
