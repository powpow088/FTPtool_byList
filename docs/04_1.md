### 模組一：SQLite 旁路快取的完整生產級封裝 (`core/sidecar_cache.py`)

在 `000.md` 中，您示範了 `stream_wafer_records` 的讀取概念，但缺少了**極速寫入端與資料表生命週期管理**。請為我們提供完整的獨立模組代碼：

1. **極速 PRAGMA 與 DDL 設計**：
   - 提供 `meta` 表與 `wafer_details` 表的標準 SQL DDL。
   - 包含讓 SQLite 在 2.5 秒內寫入 240 萬筆的關鍵連線設定（如 `PRAGMA synchronous = OFF;`、`PRAGMA journal_mode = WAL;`、`PRAGMA cache_size = 100000;`、`PRAGMA temp_store = MEMORY;`）。
2. **寫入管理器 `SidecarCacheWriter` 類別**：
   - 支援 `write_batch(records: List[Tuple])`，以批次（50,000 列）透過 `executemany` 寫入。
   - 寫入完成時，調用 `finalize(final_xlsx_path)` 自動計算檔案之 `file_size` 與 `st_mtime_ns` 並寫入 `meta` 表。
   - **異常清理防護**：若寫入過程中拋出任何 Exception，自動捕捉並呼叫 `rollback()`、關閉連線，並立即刪除尚未完成的 `.cache.db`，防止殘留髒快取。
3. **讀取管理器 `SidecarCacheReader` 類別**：
   - `is_valid(xlsx_path)`：嚴格校驗指紋（大小與毫秒級修改時間戳）。
   - `get_distinct_recipes(cache_path) -> List[str]`：在 0.05 秒內透過 SQL 撈出所有唯一的 RECIPE 清單，供樞紐表頭預先初始化。
   - `stream_records(cache_path, batch_size=50000) -> Iterator[Tuple]`：分批串流讀取。

### 模組二：彙整 1 引擎升級與雙軌串流輸出 (`core/detail_aggregator.py`)

請提供針對 `DetailAggregator` 的完整重構程式碼，滿足以下規格：

1. **雙軌寫入管道（Dual-Sink Streaming）**：
   - **管道 A（Excel 輸出）**：使用 `xlsxwriter.Workbook(temp_path, {'constant_memory': True})`。
     - **Sheet 1 (`下載清單`)**：表頭粗體、欄寬 18。
     - **Sheet 2 (`工作表2`)**：第一頁名稱為 `工作表2`（**注意：不可帶 `_01` 後綴**）。
     - **分頁機制**：單一工作表達 1,000,000 列時，自動接續建立 `工作表2_2`、`工作表2_3` 等。
     - **格式與欄寬控制**：必須在寫入資料列之前，透過 `ws.set_column()` 一次性將 A~J 欄鎖定為純文字格式 (`@`) 並設定欄寬（A:24, B:13, C:22, D:22, E:12, F:62, G:21, H:13, I:13, J:28），K 欄（`Unit BIN#`）寬度設為 13 且保留數值/General 格式。
   - **管道 B（旁路快取）**：同步將每筆解析出的晶片資料批次推入 `SidecarCacheWriter`。
2. **XML 非法控制字元防護**：
   - 整合 `sanitize_xml_text()`，自動剝除 `0x00`~`0x1F`（保留 `\t`, `\n`, `\r`），杜絕 Excel 開啟時損毀報錯。
3. **Windows 防毒鎖檔防護 (`safe_atomic_move`)**：
   - 先於本機 `%TEMP%` 產生暫存檔，完成 `wb.close()` 後，透過帶有指數退避重試（Exponential Backoff Retry）的原子移動移至目標路徑。
4. **現有進度條與日誌無縫連動**：
   - 保持現有的 `progress_cb(cur_file, total_files, written_rows, fname)` 與 `log_cb(msg)` 簽名，每 5 個檔案（及首尾）輸出進度，避免破壞現有 UI 控制。

### 模組三：彙整 2 引擎升級與兩階段極速樞紐轉置 (`core/pivot_aggregator.py`)

請提供針對 `PivotAggregator` 的完整重構程式碼，滿足以下規格：

1. **智慧路由載入器與 `calamine` 型別標準化清洗**：
   - 優先讀取 `.cache.db`；若無快取則自動切換至 `python-calamine`。
   - **型別清洗器（Type Sanitizer）**：
     `calamine` 讀出的數值可能為 `int`, `float`, `str`, `None`。請給出清晰的正規化函式：
     - `Unit BIN#`：若為 `float` 且為整數（如 `1.0`）轉為 `"1"`；若為 `int` 轉為字串；字串保留。
     - `MPID_X_Y`：確保為乾淨字串後再傳入 `pad_coordinates()`，絕不可引發 `TypeError`。
2. **兩階段樞紐轉置架構**：
   - **階段一（欄位探索）**：
     - 若命中 SQLite 快取，直接以 `SELECT DISTINCT RECIPE` 極速獲取所有 RECIPE（0.05 秒）。
     - 若走 `calamine` 退避，如何在記憶體開銷最低的情況下確定所有 RECIPE 欄位？
     - 若有空白 RECIPE，固定歸入 `ERROR_blank` 欄位並置於最右側。
   - **階段二（分頁串流寫出）**：
     - 使用 `PaginatedStreamSheetWriter` 依序寫出 `中繼明細_01...` 與 `RECIPE彙整_01...`。
     - 表頭深藍底白字（RGB: 31, 78, 120），`ERROR_blank` 深橘底白字（RGB: 198, 89, 17）。
     - 嚴格落實 **LOT 群組完整性保護**（若單一 LOT 可塞入新分頁，不在舊分頁尾端切碎）。
     - 寫入完成後，調用 `ws.activate()` 預設聚焦於 `RECIPE彙整_01` 工作表。
3. **記憶體防護與 GC 調度**：
   - 在熱迴圈中使用 `sys.intern()` 對 `PN`, `LOT`, `RECIPE`, `BIN` 做指標去重。
   - 熱迴圈前呼叫 `gc.disable()`，批次結束或換頁時呼叫 `gc.collect()` 並恢復 `gc.enable()`。
